## 2. How work reaches `main`

- The only direct commit to `main` was the initial one. Everything since arrives through an **issue → branch → PR**.
- **`main` is protected.** A PR merges only when `attribution`, `typecheck`, `lint`, `unit`, `validate`, `build` and `e2e` pass on its head and the branch is up to date with `main`. Admins can't bypass this, force pushes are blocked, and a direct push to `main` is refused.
- **Labels:** `area:engine`, `area:content`, `area:puzzle`, `area:art`, `area:audio`, `area:i18n`, `area:a11y`, `area:ci`, `area:docs`, `type:feature`, `type:bug`, `type:polish`.
- **Milestones:** M1 Foundation, M2 Engine, M3 Act I, M4 Act II, M5 Act III & Endings, M6 Polish & Release.
- Every issue has context, acceptance criteria as a checklist, a milestone and labels.
- **One branch per issue** (`<area>/<short-slug>-<issue>`, e.g. `engine/core-loop-4`). Small, focused PRs; split where a reviewer would want it split, never artificially.
- **PR description:** Summary · `Closes #n` · Screenshots (anything visual) · Test & validation evidence · Risks. End with the Claude Code attribution footer.
- **Screenshots** are committed to the orphan branch `pr-assets` under `pr-<n>/` and linked as `https://github.com/angzeli/dark-reaction/blob/pr-assets/pr-<n>/<file>.png?raw=true`. Never commit PR screenshots to `main`.
- **Before merging:** read your own diff, post a review comment on the PR with what you found, fix it, wait for green CI. For high-stakes PRs (engine core, save system, endings) a subagent that hasn't seen the work reviews the diff cold first.
- **Found a bug or a new idea mid-work?** Open an issue for it. Don't widen the current PR.
- **Update `docs/PROGRESS.md` in every PR** (what this PR merges, what's next, open decisions).

### Merging (squash, preserving authorship)

GitHub writes server-side squash commits under the account's profile display name, which is not "Angze Li", so a plain "Squash and merge" would break §1. We squash locally instead and let GitHub fast-forward the single commit:

1. When the PR is ready: `git fetch origin main && git reset --soft origin/main` on the PR branch (rebase first if `main` moved).
2. Commit once, with subject `<PR title> (#<n>)`, a body summarising the change, ending with the trailer. Write the message to a file and use `git commit -F <file>` (the equivalent of `--body-file`).
3. `git push --force-with-lease` the PR branch (it's our own branch). Wait for CI to go green on that commit.
4. Merge with the **rebase** method (GitHub MCP `merge_pull_request`, `merge_method: "rebase"`). With one commit this lands exactly that commit, author intact.
5. `git checkout main && git pull --ff-only` and verify: `git log -1 --format='%an <%ae>%n%B'` must show Angze Li, the `(#n)` subject and the trailer.

## 3. Commands

| Command | What it does |
|---|---|
| `npm ci` | Install exact dependencies (Node ≥ 22.18; scripts run under Node's built-in type stripping) |
| `npm run fonts` | Subset the self-hosted fonts to the glyphs in use (`src/assets/fonts/generated/`, gitignored); runs before `dev` and `build` |
| `npm run dev` | Vite dev server at `http://localhost:5173/dark-reaction/` |
| `npm run build` | Subset fonts, typecheck, then build to `dist/` (production builds inject a strict CSP with `connect-src 'none'`) |
| `npm run preview` | Serve `dist/` at `http://localhost:4173/dark-reaction/` |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint (flat config, typescript-eslint; bans enums, namespaces and network globals in `src/`) |
| `npm test` | Vitest unit tests in `tests/` |
| `npm run validate` | Content validator (graph, endings, locale parity, placeholders, playtime) |
| `npm run e2e` | Playwright against the built site (`npm run build` first; pass `-- --trace off` locally) |
| `bash scripts/check-attribution.sh origin/main..HEAD` | Attribution check for your branch |

CI runs `attribution`, `typecheck`, `lint`, `unit`, `validate`, `build` and `e2e` on every PR; `deploy.yml` publishes `dist/` to GitHub Pages on every push to `main`. Playwright is pinned to 1.63.0 to match the browser preinstalled in the cloud container; keep them in step.

## 4. Code conventions

- **TypeScript strict**, ES modules, no UI framework. Import local files with explicit `.ts` extensions and use only erasable syntax (no `enum`, no `namespace`, no parameter properties) so scripts run directly under Node's type stripping.
- **Minimal dependencies.** Every new dependency is justified in its PR description.
- **Data-driven story.** Scenes, choices, conditions, effects, the clock, loop rules and notebook entries live in typed files under `src/content/`. Engine code never contains story text.
- **Every player-visible string is a key**, looked up with `t(key, params)` from `src/i18n/i18n.ts`. Tables are split by area: `src/i18n/en/<area>.ts` and its twin `src/i18n/zh-Hant-TW/<area>.ts`, which is typed `Record<keyof typeof en, string>` so the compiler enforces parity. `src/i18n/en.ts` and `src/i18n/zh-Hant-TW.ts` merge the areas. Keys are dotted and scoped: `office.hub.act1`, `office.kettle.look`, `nb.queue.0333.title`, `puzzle.tlc.hint.2`. Placeholders are `{name}` and must match across locales; English plurals use `{n:minute:minutes}`; a param value `@some.key` is itself looked up. Missing keys render as `[[key]]`.
- **Both locales are originals.** English uses British spelling. Chinese is 國語 in Traditional characters, Taiwanese usage, full-width punctuation with 「」.
- **Pure logic is separated from DOM.** Engine and puzzle rules live in modules with no DOM access, so Vitest and the validator can drive them headlessly. UI modules only render state and forward input.
- **Puzzles** export a pure `logic` (state, moves, `isSolved`, a known solution for the bot) and a `view` (DOM). Each has three hint keys and a par time.
- **No runtime network requests**, no analytics, no telemetry. All assets ship with the build.
- **Accessibility is not optional:** every interaction works by keyboard and touch, nothing depends on hover, motion and flicker respect settings, text meets contrast in high-contrast mode.
- **Content boundaries:** no suicide or self-harm, no gore, no real hazardous procedures (see `docs/DESIGN.md` §1).
- **Tests:** engine and puzzle logic get Vitest coverage; anything the player can do end to end gets a Playwright path.
- Third-party assets must be OFL or CC0 and listed in `CREDITS.md`.
- **UI** (`src/ui/`): `App` in `app.ts` renders from engine state and owns screens (title, play, ending), overlays (notebook, menu), transition cards, the puzzle overlay and autosave (after every action and card). `settings.ts` holds player settings (separate key, applied as `<html>` data attributes: `data-motion`, `data-flicker`, `data-contrast`, `data-text-size`). `reveal.ts` reveals text without hiding it from screen readers. `window.darkReaction` exposes the `App` for the Playwright bot only.
- **Unicode escapes in tool input:** some editing tools decode `\uXXXX` before writing, which puts literal (sometimes invisible) characters into source. In regexes, build escapes another way (e.g. Python `chr(92) + 'u3000'`) and check with `cat -A`.
- **Art:** scenes are pure functions `(ArtContext) => string` returning SVG in a 1600 × 900 viewBox (`src/art/scenes/`, registered in `scenes/index.ts`), built from the helpers in `src/art/svg.ts` and the palette `C`. The stage crops with `slice`, so keep what matters inside the safe band x 200–1400, y 150–760, and the essentials inside y ≈ 240–660: at common desktop sizes the play screen shows only about that much of the 900-unit height. Randomness only through `seeded(hash(id))` so a scene never changes between renders. Motion only through the CSS classes in `src/styles/art.css` (`dr-rain`, `dr-drop`, `dr-flicker`, `dr-blink`, `dr-breathe`), which the reduce-motion and flicker settings switch off. Illustrations are `aria-hidden`; the location is described in text.
